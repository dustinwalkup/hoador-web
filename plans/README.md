## Ranking rationale

1. **009 → 011: live money bugs on mobile-used endpoints.** Mobile calls
   `/api/services/bookings/[id]/{accept,complete,cancel}`. After a
   post-charge failure, 009 can still double-charge a customer, either on a
   retry with a different card or through two concurrent retries; the F12
   fix only covers retries on the same card. 011 is now worse than written.
   The late-cancel provider transfer (`service-cancel-transfer-*`) and the
   payout cron (`service-transfer-*`) use different idempotency keys, so a
   complete/cancel race can refund the customer _and_ pay the provider
   twice. 011's cancel guard only works once 009's `processing` claim
   exists.
2. **010: small and exploitable today.** Anyone with an account can delete
   anyone's profile image, and anonymous callers can spend the paid SERP API
   key. It needs no coordination with the other plans, so it can go first
   if you want a quick win.
3. **012 and 015: pin backend behaviour before mobile builds on it.**
   Mobile Epic 13.1 (reviews) and 13.2 (disputes) are next. Each test plan
   should land before the matching epic.
4. **014: reliability of the only remaining signal.** Once the web app is
   gone, push and email are how users learn about review releases and
   payouts. A failed notification should not count a successful payout as
   failed, and it should reach Sentry.
5. **013 Part A:** the N+1 is in the mobile explore feed, but pages are capped
   at 12 items, so this is a performance fix rather than a correctness fix.
6. **005 and 004 remainders: no double-charge exposure.** Both are UX
   dead-ends: a rental stuck in `processing`, and a failed deposit retry on a
   new card. Both need a human design call.

## Dependency notes

- **009 before 011**: both rewrite `service-booking-service.ts`. Never run
  them in parallel worktrees.
- **009 is the service-side twin of 004/005.** It was designed around their
  BLOCKED findings: a catch that resets to a retryable status after a
  successful charge re-arms a double charge. Its post-charge failure handler
  deliberately leaves the booking claimed. See plan 009's "Maintenance
  notes".
- **012 and 014 can land in either order, but they are coupled.** 012 tests
  the reviews service's notification-failure behavior, and 014 changes it
  (`console.error` → `captureNonCriticalError`). Whichever lands second
  reconciles the assertions.
- **004 Step 3 is blocked.** The cron's `findScheduledDepositsNearPickup`
  selects both `scheduled` _and_ `failed` rows and deliberately retries
  failed holds. A per-payment-method key on the renter retry alone would let
  a concurrent cron and retry place two holds. The fix needs one of two
  decisions: a shared payment-method-scoped key for cron and retry, or
  excluding `failed` from the cron query.
- **005 Step 3 is blocked.** Resetting to `failed` in a catch-all would turn
  today's post-charge `processing` stall into a double charge, because a
  retry takes the `Date.now()` key. Recommended rescope: extend the
  existing `detect-stale-processing` cron to cover
  `rentalRequests.paymentStatus = 'processing'`, and alert ops.
- `docs/payment-lifecycle-unification.md` (the output of the removed plan
  008, verdict GO-LATER) should be re-baselined once 009 and 011 land.
- 010, 013 and 015 are independent of everything else.
