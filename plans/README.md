## Ranking rationale

1. **010: small and exploitable today.** Anyone with an account can delete
   anyone's profile image, and anonymous callers can spend the paid SERP API
   key. It needs no coordination with the other plans.
2. **012 and 015: pin backend behaviour before mobile builds on it.**
   Mobile Epic 13.1 (reviews) and 13.2 (disputes) are next. Each test plan
   should land before the matching epic.
3. **014: reliability of the only remaining signal.** Once the web app is
   gone, push and email are how users learn about review releases and
   payouts. A failed notification should not count a successful payout as
   failed, and it should reach Sentry.
4. **013 Part A:** the N+1 is in the mobile explore feed, but pages are capped
   at 12 items, so this is a performance fix rather than a correctness fix.
5. **005 and 004 remainders: no double-charge exposure.** Both are UX
   dead-ends: a rental stuck in `processing`, and a failed deposit retry on a
   new card. Both need a human design call.

## Dependency notes

- **012 and 014 can land in either order, but they are coupled.** 012 tests
  the reviews service's notification-failure behavior, and 014 changes it
  (`console.error` → `captureNonCriticalError`). Whichever lands second
  reconciles the assertions.
- **004 Step 3 is blocked.** The cron's `findScheduledDepositsNearPickup`
  selects both `scheduled` _and_ `failed` rows and deliberately retries
  failed holds. A per-payment-method key on the renter retry alone would let
  a concurrent cron and retry place two holds. The fix needs one of two
  decisions: a shared payment-method-scoped key for cron and retry, or
  excluding `failed` from the cron query.
- **005 Step 3 is blocked.** Resetting to `failed` in a catch-all would turn
  today's post-charge `processing` stall into a double charge, because a
  retry takes the `Date.now()` key. Recommended rescope: extend the
  existing `detect-stale-processing` cron to cover
  `rentalRequests.paymentStatus = 'processing'`, and alert ops.
- `docs/payment-lifecycle-unification.md` (plan 008's output, verdict
  GO-LATER) should be re-baselined on 009/011's claim and CAS semantics.
- **Follow-ups left by 009/011** (unplanned): a service booking whose charge
  succeeded but whose persistence failed stays claimed
  (`paymentStatus = "processing"`) with only an ops alert, and there is no
  stale-claim detector yet (same gap as 005's rescope; one detector could
  cover both). `declineBooking` is still an unguarded update and can race an
  in-flight accept.
- 010, 013 and 015 are independent of everything else.
