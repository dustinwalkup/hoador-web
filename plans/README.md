## Dependency notes

- `docs/payment-lifecycle-unification.md` (plan 008's output, verdict
  GO-LATER) should be re-baselined on 009/011's claim and CAS semantics, and
  on 004's deposit semantics (renter-only retry of `failed` holds,
  card-scoped retry key).
- **Follow-ups left by 009/011** (unplanned): `declineBooking` is still an
  unguarded update and can race an in-flight accept. (A booking left claimed
  after a post-charge persistence failure is now surfaced hourly by 005's
  `detect-stale-charge-claims` cron.)
- **Follow-ups left by 004/005** (unplanned):
  - `RentalDAL.approveRentalRequest` is not a transaction. It marks the
    request `approved` / `succeeded` before inserting the `rentals` row, so an
    insert failure leaves a paid, approved request with no rental, and the
    stale-claim detector can't see it.
  - Approve and renter-cancel of a pending request still aren't serialized.
    The detector now catches the charged-and-cancelled outcome but nothing
    prevents it.
  - The stale-charge-claim alert repeats hourly until someone resolves the
    claim, and there's no admin action for that; the fix is manual in Stripe
    and the DB (the alert text says how).
  - The approval-time deposit hold keys on the rental _request_ id
    (`deposit-hold-{requestId}`), the cron on `rentals.id`. That's harmless
    today because they never act on the same state, but the keys should be
    unified if the lifecycles are (008).
  - UAT-P1-10 and UAT-P1-16 in `specs/payments/4-uat-test-plan.md` were
    rewritten for the new retry flow and need re-running. The web
    `retry-deposit-button` copy was left alone (web UI retiring).
- **Follow-ups left by 015** (unplanned):
  - `PUT /api/disputes/[id]/notes` saves the edit **before** checking the note
    belongs to the dispute, so an admin can change another dispute's note and
    still get a 400. Admin-only; the fix is to check membership first, as
    DELETE does. The notes test pins today's behaviour and says which
    assertion to flip.
  - `PATCH /api/disputes/[id]/state` never checks the caller is a party; its
    only authorization is every target being in `ADMIN_ONLY_STATES`. The state
    test fails if that changes, which is the moment to add a party check.
  - Two dispute tests still mock `route-helpers` wholesale: the list/create
    route (`disputes/__tests__/route.test.ts`, which mobile Epic 13.2 calls
    for create) and `[id]/resolve`. Convert them when next touched.
